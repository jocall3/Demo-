# 10. Implement Zero-Trust Secret Management with HashiCorp Vault

## Status

Accepted

## Context

Our current approach to managing secrets (database connection strings, API keys, JWT signing keys) is fragmented and insecure. Secrets are stored in a combination of `.env` files, Docker Compose files, and CI/CD environment variables. This practice has several critical drawbacks:

1.  **Security Risk**: Secrets are often stored in plaintext or are easily accessible to anyone with access to the CI/CD system or the host environment. `.env.example` files, while not containing secrets, reveal the *shape* of our secrets, which is an information leak.
2.  **Lack of Auditability**: There is no central audit trail for who accessed which secret and when. This makes compliance and incident response incredibly difficult.
3.  **Difficult Rotation**: Secrets are static and long-lived. Rotating a compromised secret requires manual changes across multiple files and systems, followed by a full redeployment, making the process slow and error-prone.
4.  **Static Credentials**: We rely on static, long-lived database usernames and passwords, which, if compromised, provide long-term access to our data stores.
5.  **Developer Experience**: Developers often need access to production-like secrets for local development, which increases the risk of accidental leakage.

A zero-trust architecture mandates that no entity is trusted by default. This principle must extend to how our applications handle and access secrets. We need a centralized, secure, and dynamic way to manage the lifecycle of all credentials.

## Decision

We will adopt HashiCorp Vault as the single, centralized source of truth for all secrets across the entire platform.

1.  **Centralization**: All secrets will be removed from `.env` files, Docker Compose files, CI/CD variables, and source code. Every microservice will be reconfigured to fetch its required secrets from Vault at startup.

2.  **Authentication**: Services will authenticate to Vault using the **AppRole authentication method**.
    -   Each service (or service instance) will be assigned a unique, non-secret `RoleID`.
    -   During deployment, our CI/CD pipeline will generate a single-use, wrapped `SecretID` for the service instance.
    -   The service instance will use the `RoleID` and unwrap the `SecretID` to obtain a short-lived Vault token. This token will be used to retrieve its necessary secrets.

3.  **Dynamic Database Credentials**: We will implement Vault's **Database Secrets Engine**.
    -   Vault will be configured to connect to our databases with a high-privilege user.
    -   Microservices will no longer use static database credentials. Instead, at startup, they will request a unique, dynamically generated username and password from Vault.
    -   These credentials will have a short Time-To-Live (TTL) (e.g., 1 hour) and will be automatically revoked by Vault upon lease expiration, dramatically reducing the risk associated with compromised credentials.

4.  **Secret Engines**:
    -   **KV v2 Secrets Engine**: For static secrets like third-party API keys (e.g., Plaid, Stripe, Google Gemini), we will use the Key-Value v2 engine to enable versioning and simple key-value storage.
    -   **Transit Secrets Engine**: For "encryption-as-a-service," services will use the Transit engine to encrypt sensitive data before storing it in their own databases (e.g., Plaid access tokens). This ensures the application code never handles the raw encryption keys.

## Consequences

### Positive

*   **Drastically Improved Security**: Secrets are no longer hardcoded or stored in insecure locations. They are centralized, encrypted at rest, and accessed via authenticated and authorized clients.
*   **Centralized Management & Auditability**: Vault provides a single control plane for managing and auditing all secret access, which is crucial for security posture and compliance.
*   **Dynamic Credentials & Automatic Rotation**: The use of the Database Secrets Engine eliminates the problem of static, long-lived database passwords. Credentials become ephemeral and are automatically rotated and revoked.
*   **Reduced Attack Surface**: The TTL on secrets and tokens limits the window of opportunity for an attacker if a credential is compromised.
*   **Improved Developer Workflow**: Developers can run a local Vault instance for development, using the same secret access patterns as production without needing access to production secrets.

### Negative

*   **Increased Operational Complexity**: We are introducing a new, critical piece of infrastructure. Vault must be deployed, managed, and maintained with a high-availability configuration, as it is now a single point of failure for application startup.
*   **Application-Level Changes**: Every microservice requires modification to include a Vault client, logic for AppRole authentication, and secret fetching at startup. This is a significant, cross-cutting development effort.
*   **Increased Startup Latency**: Services will experience a slight increase in startup time as they need to perform an authentication handshake with Vault and fetch their secrets over the network before they can fully initialize.
*   **New Failure Mode**: An outage or misconfiguration of Vault can prevent services from starting or renewing their credentials, potentially leading to a cascading failure across the platform. This necessitates robust monitoring and alerting for Vault itself.
